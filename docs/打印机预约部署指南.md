# 拓竹杯打印机预约：本地与云端部署

## 功能与使用

公开入口 `/printer-booking`，管理员入口 `/admin/printers`。三台打印机各自校验时间冲突，同一队伍可以同时预约三台机器。查询直接使用现有拓竹杯赛事队伍数据：输入队长学号，查到有效队伍后即可预约，符合规则立即成功，无需审批。队员学号不能作为预约查询身份。

本页不登记新队伍、不设置队伍口令、不使用邀请码。未报名的同学通过页面上的“前往赛事报名”进入对应 `/team-portal?event_id=ID` 页面。管理员在打印机管理页选择绑定的拓竹杯赛事；系统能唯一识别含“拓竹”名称的赛事时可自动关联，多个候选时需明确选择，不能随意绑定其他赛事。管理员也可直接添加或删除预约。

办公室开始时间限制默认关闭；实际开放时间确认后，在打印机管理页按星期设置并启用。只约束开始时间，结束可以在关门后或次日。所有预约以北京时间显示和校验。

预约进度自动随时间变化：开始前“待使用”，到开始时间“使用中”，到结束时间“已结束”；页面每秒更新，无需刷新。已取消、实际归还优先；实际已签到但尚未归还，即使超过预约结束时间仍显示“使用中”。自动进度不会生成签到记录，现场使用仍需签到、结束归还，以保留准确的异常追溯依据。本次状态修复不需要额外数据库迁移，更新后端并上传新前端包即可。

每次使用先签到，结束归还。接机时发现异常，通过对应预约报告，系统追溯上一实际使用队伍并保存快照；无上一使用记录时显示无历史。异常报告使机器进入维护状态，由管理员处理并确认恢复。追溯依据是系统记录，管理员应结合现场情况记录处理结果。

## 数据库增量更新

沿用生产 `.env` 的 MySQL 配置和现有赛事、队伍表。打印预约通过现有 `teams` 主键关联队伍，不需要复制一份队伍或搬运本地测试数据。上线前备份现有数据库。云端数据库若位于其他主机，仍只需配置 `DB_HOST`、`DB_PORT`、`DB_USER`、`DB_PASSWORD`、`DB_NAME`；凭据只保留在服务器 `.env`。

```bash
cd /var/www/all-in-one
# 提示输入数据库密码；将用户和数据库名替换为实际配置
mysqldump -u club_user -p --single-transaction --routines --triggers club_management > "$HOME/club-before-printers-$(date +%Y%m%d-%H%M%S).sql"
source .venv/bin/activate
python -m scripts.init_printers
```

初始化脚本创建缺失的打印机表、补齐三台机器，并增量升级上一版预约关联字段，可重复执行。全新部署不创建独立打印队伍表；已部署上一版时保留旧表作为历史，不再用于查询或登记。旧预约只有按原赛事及队长学号唯一匹配现有队伍后才迁移归属，未匹配记录保留，不能强行分配给相同数字ID的队伍。不要运行数据库重建脚本或把测试库覆盖到生产库。新表使用 InnoDB 事务锁处理同机并发预约，生产应使用 MySQL。升级脚本需要目标库 `CREATE`、`ALTER` 和索引/外键相关权限。

## 按你的流程发布

下面示例服务器目录沿用项目部署文档 `/var/www/all-in-one`，后端服务名 `club-backend`。请替换 SSH 用户、服务器地址及实际目录。发布期间暂停操作，先更新数据库和后端，再切换前端。

### 1. 云端拉取后端

本次提交推送在 `ZHM` 分支。服务器若部署在其他分支，先确认采用的发布分支并合入本次提交，避免直接把旧分支部署回去。

```bash
cd /var/www/all-in-one
git status --short
git fetch origin
git switch ZHM
git pull --ff-only origin ZHM
source .venv/bin/activate
pip install -r requirements.txt
# 上一版已部署时，先暂停旧服务写入，再执行增量升级
sudo systemctl stop club-backend
python -m scripts.init_printers
sudo systemctl start club-backend
sudo systemctl status club-backend --no-pager
curl --fail http://127.0.0.1:8001/health
curl --fail http://127.0.0.1:8001/api/v1/printers/config
```

`git status` 若有服务器本地代码修改，先备份并处理；保留生产 `.env` 和 `uploads`。初始化应使用与服务相同的 `.env`。若 MySQL 是托管云数据库，数据库账号需要在目标库中创建新表和索引的权限，初始化后服务仍使用同一数据库连接。

### 2. 本地编译前端并 SCP

在本地 PowerShell 中运行：

```powershell
cd D:\SCUT-wuxie-code\all-in-one\frontend
npm ci
# 使用同源 /api，避免包中写入 localhost；空值也由新模块正确处理
$env:VITE_API_BASE_URL = "/api"
npm run build
Remove-Item Env:VITE_API_BASE_URL
# 先上传到新的待发布目录，不直接覆盖正在服务的 dist
ssh deploy@YOUR_SERVER "mkdir -p /var/www/all-in-one/frontend/dist-printers-next"
scp -r .\dist\* deploy@YOUR_SERVER:/var/www/all-in-one/frontend/dist-printers-next/
```

再次发布时使用新的空待发布目录，例如增加日期后缀，防止旧文件残留。Vite 打包文件带哈希，前后端需按同一版本发布。

### 3. 云端切换静态文件

确认上述路径确实对应 Nginx 正在使用的目录后执行。保留上个版本用于回退：

```bash
cd /var/www/all-in-one/frontend
mv dist "dist-before-printers-$(date +%Y%m%d-%H%M%S)"
mv dist-printers-next dist
sudo nginx -t
sudo systemctl reload nginx
```

Nginx 需要支持 Vue 路由刷新，并保持 `/api` 前缀转发到后端：

```nginx
location / {
    root /var/www/all-in-one/frontend/dist;
    try_files $uri $uri/ /index.html;
}
location /api/ {
    proxy_pass http://127.0.0.1:8001;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
}
```

这里 `proxy_pass` 后不加 `/`，确保后端收到 `/api/v1/printers/...`。已有相同配置无需修改。

### 4. 上线验收

1. 打开 `/printer-booking` 并刷新，确认三台机器和日程正常加载。
2. 管理员登录，打开 `/admin/printers`，确认绑定现有拓竹杯赛事；按实际办公室时间决定是否启用开始限制。
3. 输入该赛事队伍的队长学号并预约；队员学号/其他赛事队长查不到，查不到时可跳转对应报名页。同队可在三台设备预约相同时段，同机重叠时间应被拒绝。管理员直接添加和删除测试预约，验证无需审批。
4. 验证取消、签到、归还和异常追溯。测试完成取消测试预约；不要为测试修改真实使用历史。
5. 手机打开同一路径，确认按钮、表单和日期选择可用。
6. 后端日志查看 `sudo journalctl -u club-backend -n 100 --no-pager`。

## 回退

先停止预约操作，并记录发布前的代码版本与数据库备份。新版预约关联现有 `teams`；上一版代码只认识独立打印队伍，因此本次升级后不能仅回退上一版后端并继续开放预约，否则新预约的归属无法被旧代码正确识别。需要回退时，应保持预约入口暂停，前后端作为一组切回备份版本，并评估是否恢复对应数据库备份；恢复前另行备份升级后的预约及异常记录，确认不会遗漏新记录。不要删除旧表或直接覆盖数据库。
